# 다층 환각 검증 파이프라인

**제품의 존재 이유다. 임의로 단순화하지 말 것.** 과제계획서의 "AI 환각으로 부정확한 데이터 도출 방지" 요구사항에 직접 대응한다.

## 4층 구조

| 층 | 내용 | LLM 호출 |
|---|---|---|
| ① 출처 인용 검사 | 뉴스 항목별 출처·링크 존재 및 URL 형식, 출처커버리지 계산 | 없음 |
| ② LLM-as-judge | 분석결과가 뉴스 원문에 근거하는지 문장 단위 채점 (temperature=0) | 있음 |
| ③ evidence-match | 분석결과와 원문의 어휘적 겹침 측정 | **없음** |
| ④ 반증 분석 | "이 평가가 틀릴 수 있는 이유" 자동 생성 | ② 프롬프트에 포함 |

③은 LLM 없이 계산한다. ②만으로는 judge 자체의 오판을 걸러낼 수 없기 때문에 독립적인 기계적 신호가 필요하다.

④의 결과는 평가위원회 자료의 **유의사항**으로 노출한다. 숨기지 않는다.

## 판정 규칙

```
faithfulness ≥ 0.85  AND  출처커버리지 ≥ 0.5  AND  evidence-match ≥ 0.4
  → verified
그 외 전부 → needs_review
```

**오류·파싱 실패·타임아웃은 무조건 `needs_review` 다.** 검증 실패 = 신뢰 불가 원칙이다. `try/catch` 에서 기본값을 `verified` 로 두는 코드를 쓰지 않는다.

임계치 미달은 사람 최종 확인 게이트로 넘어간다 — 자동 통과시키지 않는다.

## 파이프라인 통합 규칙

- 분석 완료 후 **비동기 지점**에서 실행한다. 검증이 실패해도 기존 리포트 생성은 정상 완료돼야 한다
- 진행 상태는 SSE 이벤트로 프론트엔드에 전달한다
- 결과는 `VerificationResult` 로 저장한다 — 상태·점수 2종·미확인 주장 목록·전체 결과 JSON
- 벤치마킹에서 `verified` 는 가점이다. 리스크 알림은 **담당자가 확인한 것만** 감점에 반영한다 (오탐 방지)

## 산식 버전

`SelectionRecord` 에 산식 버전 필드를 포함한다. 점수 산식이 바뀌면 연도별 추이 비교가 왜곡되므로, 버전이 다른 구간을 비교할 때 주석을 표기한다.
